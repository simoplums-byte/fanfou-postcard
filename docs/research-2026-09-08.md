## 结论摘要

### `heedless/fanfou-backup` 还能不能用？

结论是：**不能合理地认为 README 中的原始方法可以直接使用；经现代化改造后，其 API 导出思路仍可能可用。**

截至本次检查：

- GitHub 仓库仍可访问，HEAD 为 `9efe17db1aec16c1f2b2494b507c5c38baa62a6b`。
- 仓库只有 4 次提交，最后一次提交时间为 2016-05-04。
- 入口和依赖明确使用 Python 2：`print` 语句、`raw_input`、`urllib2`、`urlparse`，现代 macOS 通常不会预装 Python 2。
- 所有 API 与 OAuth 地址写死为 `http://`。
- 需要用户自行填写 consumer key/secret；access token 以明文写入项目根目录的 `oauth2.db`。
- 分页导出通过不断增加 `page`，直至响应恰好等于 `[]`；没有超时、重试、限流退避、重复页检测、断点续传或结构校验。
- JSON 是把每页响应文本直接追加后再替换 `]\n\n[`，中断可能留下损坏文件；XML 采用类似的文本拼接。
- 它只导出消息，不导出照片文件、好友、收藏、私信，也没有完整性清单。

因此，不应把“仓库还在线”理解为“工具仍可运行”。若要复用，至少需要替换运行时与 OAuth/HTTP 客户端、改为安全凭据存储、添加稳健分页与断点续传，并以原子方式生成 JSON。

### 饭否 API 本身是否仍支持这条路线？

证据是混合的：

- 饭否 API 文档仍记录 `GET /statuses/user_timeline`，支持 `id`、`since_id`、`max_id`、`count`（1–60）和 `page`。但该 Wiki 页面本身最后编辑于 2012 年，说明“接口设计存在”，不能单独证明 2026 年生产服务可用。
- `fanfou-sdk` 的 npm 包仍在维护，检索时显示 6.0.0，且示例仍包含 OAuth、XAuth 和 timeline。这是生态仍在活动的旁证，不是对个人账号导出成功的直接验证。
- 2026-09-08 对 `https://api.fanfou.com/statuses/public_timeline.json?count=1` 的无凭据只读探测返回 HTTP 404。饭否主域名也可连接但根路径返回 404。这个结果既不是 200，也不是明确的 401/403，无法据此确认鉴权后的 API 是否可用。
- 本次没有 consumer key/secret 和账号授权，因此没有做 `verify_credentials` 或个人 timeline 的真实调用。

目前最准确的表述是：**路线具有现实可行性，但尚未通过账号级端到端验证。** 是否可导出受有效饭否应用凭据、OAuth 地址/协议和账号权限共同影响。

## 推荐的 Fanfou Postcard 路线

### 阶段 1：最小只读验证

前置条件是用户拥有有效的饭否 consumer key/secret，或者能在饭否侧申请/恢复应用凭据。

1. 凭据仅通过环境变量或本机权限受限的凭据文件注入，不写入仓库、命令历史或日志。
2. 先调用 `account/verify_credentials`。
3. 只抓个人时间线最新 1 页（最多 20–60 条），不下载照片。
4. 保存 HTTP 状态、响应内容类型、记录数和字段清单；原始响应中的敏感令牌绝不落盘。
5. 检查 ID 唯一性、时间排序、转发/回复/照片字段，以及 `statuses_count` 与可见记录数的差异。

只有这一步成功，才把 API 路线标为“当前可用”。

### 阶段 2：完整、可恢复的 JSON-first 备份

- 权威产物：版本化 manifest + 原始/规范化 JSON，UTF-8，无损保留未知字段。
- 分页：优先使用 `max_id`/`since_id`；检测重复页和无进展页；每页落 checkpoint。
- 完整性：记录抓取开始/结束时间、账号 ID、页数、唯一 ID 数、最早/最晚消息、失败页和内容哈希。
- 增量：后续从最新已知 ID 更新；历史回补和新消息更新分开。
- 媒体：先保存照片原始 URL 和归属消息，照片下载作为可恢复的独立步骤。
- 查看副本：SQLite/HTML/Markdown/CSV 均由权威 JSON 生成。
- 不扩大范围：收藏、私信、好友资料分别评估权限与隐私后再加，不能默认为“个人消息备份”的一部分。

### 实现选择

建议优先从 `fanfou-echo` 抽取 API、SQLite 与渲染经验，但在 `fanfou-postcard` 建立新的、较窄的 JSON-first 核心。原因是 Echo 同时背负 GUI、旧模板、多格式渲染和历史兼容，直接继承会让“备份完整性”与“展示功能”继续耦合。

在最小实测前，不需要立刻编写完整导出器。最大的未知数不是代码，而是有效应用凭据和饭否生产 API 当前的实际响应。

### OAuth 与 API 实测结果

后续实测进一步确认：

- consumer key/secret 已保存于 macOS 登录钥匙串，没有写入仓库；
- Request token 请求成功；饭否要求实际走 HTTPS，但 OAuth basestring 使用 HTTP（fake HTTPS 兼容）；
- 浏览器 PIN/OOB 授权成功；
- Access token 交换成功，token 与 secret 已保存于 macOS 登录钥匙串；
- `account/verify_credentials` 返回 HTTP 401，错误为“参数错误”；
- `statuses/user_timeline?count=1&mode=lite` 同样返回 HTTP 401“参数错误”；
- 自写 HMAC-SHA1 探针和 `requests-oauthlib 2.0.0` 对照实现结果完全一致；切换签名基址时服务端能明确返回预期 basestring，说明当前签名链路可诊断且 HTTP basestring 是正确选择；
- 应用详情页仍显示“未审核”。

因此当前判断是：**OAuth 基础设施仍可工作，但新建且未审核的应用暂时不能访问受保护资源 API。** 这是目前概率最高的解释；饭否没有返回更具体的审核错误码，因此仍需通过应用审核或饭否开发者支持确认。完整导出代码不应在这个阻塞解除前被宣称可用。

已用完的临时授权 URL 和一次性 request token 已清理；长期 consumer 凭据和 access token 保留在 macOS 钥匙串，供审核通过后复测。
